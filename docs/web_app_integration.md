# Web Application Integration Plan for SpaceLayoutGym

This document outlines a reference architecture for wrapping SpaceLayoutGym in a user-facing web application where visitors can sketch a floor-plan contour, specify design constraints, and receive candidate layouts generated by back-end agents. The same pipeline also records user selections for future training.

## High-Level Architecture
1. **Frontend (Web Client)**
   - Canvas-based polygon editor for drawing floorplan contours and marking entrances/orientation.
   - Form widgets for room counts, target areas, adjacency preferences, and other constraints.
   - Gallery view for candidate layouts returned by the server, allowing rating/bookmarking.

2. **Backend API Service**
   - Python/FASTAPI (or similar) server that exposes endpoints:
     - `/api/config` to translate user JSON payload into a `LaserWallConfig` override.
     - `/api/generate` to run SpaceLayoutGym episodes with the desired solver/policy.
     - `/api/feedback` to store the chosen layout, rating, and metadata.
   - Manages persistence (SQL/NoSQL) for user sketches, generated layouts, rewards, and selection logs.

3. **Computation Layer**
   - Wraps the Gym environment and the trained policy (RLlib PPO, scripted heuristic, etc.).
   - Supports batch evaluation to quickly produce multiple candidate layouts per request.
   - Provides headless rendering via Matplotlib to return PNG/JSON geometry.

## Data Flow
1. User sketch & constraints submitted as JSON (vertices, entrance locations, target areas, etc.).
2. Backend converts the payload into the format expected by `AdjustableConfigsHandeler`, creating a new `plan_config_source_name` for "user_upload" scenarios.
3. Environment is instantiated with merged configuration (`default_hps_env.yaml` + overrides).
4. Policy agent generates N rollouts; each accepted episode yields:
   - Rendered images (PNG/SVG) and serialised wall placement sequence.
   - Episode metrics (reward, constraint satisfaction flags, adjacency matrices).
5. Backend responds with candidate layouts plus metadata for the frontend gallery.
6. User selection/feedback is POSTed back and stored for offline reinforcement learning or supervised finetuning.

## Key Engineering Tasks
- **User Sketch Parsing**: Convert free-form polygons into the grid-based mask lengths/widths and entrance descriptors expected by `PlanConstructor`. Implement snapping to valid wall coordinates to ensure compatibility.
- **Config Extension**: Add support in `AdjustableConfigsHandeler` for a new `plan_config_source_name="user_uploaded"` branch, accepting direct payloads instead of pre-defined scenarios.
- **Policy Runner Service**: Expose a coroutine-friendly wrapper that loads the PPO policy once, then serves inference requests without reinitialising the environment on every call.
- **Rendering Pipeline**: Reuse `RenderPlan` in off-screen mode (Agg backend) to produce images; optionally include vector (GeoJSON) outputs for frontend overlays.
- **Data Logging**: Standardise schemas for episodes, user actions, and derived metrics. Consider storing both raw geometry and summary statistics.

## Operational Considerations
- **Scalability**: Use task queues (Celery, Redis) or async workers to handle heavy batch generation.
- **Model Management**: Version policies and environment configs; include metadata with every generated layout for reproducibility.
- **Security**: Sanitize uploads, limit polygon complexity, and enforce authentication if needed.
- **Monitoring**: Track request latency, policy inference time, and conversion rates from generated to accepted layouts.

## Next Steps
1. Prototype the JSON schema for user inputs and ensure round-trip compatibility with SpaceLayoutGym.
2. Implement a minimal FastAPI service that exposes `/api/generate` using the random agent as a stub.
3. Integrate a simple frontend (e.g., React + Konva) to draw polygons and visualise returned layouts.
4. Gradually swap in trained PPO agents and add persistence for user feedback.
